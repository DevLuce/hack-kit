# hack-kit

**이해 → 실행 → 검증**으로 과제를 진행하고, 판단과 검증 근거를 남기는 작은 도구 모음입니다.

Python 3.11 이상과 표준 라이브러리만으로 실행합니다. 별도 AI 모델·API 키·서버가 필요하지 않습니다.
제출용 완성 프로젝트나 특정 문제의 정답 코드는 포함하지 않습니다.

## 시작하기

공개 주소: **https://github.com/DevLuce/hack-kit**

```sh
git clone https://github.com/DevLuce/hack-kit.git
```

제공된 코딩 에이전트에 다음처럼 요청하세요.

> hack-kit의 README와 skills/task-workflow/SKILL.md를 읽어줘.
> 현재 과제의 안내와 기존 코드부터 확인하고, 이해 단계만 진행해줘.
> 원인·완료 기준·해결 계획을 설명하되 사실과 가정을 구분하고, 아직 구현하지 마.

Skill 자동 발견·설치 여부는 실행 환경마다 확인해야 합니다. 이 저장소를 Clone했다고 자동으로
활성화되었다고 가정하지 마세요. 제공 환경의 Skill 안내를 따르거나 위처럼 파일 읽기를 명시합니다.
기존 프로젝트 지침·설정 파일을 덮어쓸 필요는 없습니다.

## 세 단계 프롬프트

1. **이해:** 요구사항과 기존 코드·자료를 분석해서 원인·완료 기준·해결 계획을 정리해줘.
   확인된 사실과 가정을 구분하고, 모호한 점은 질문해줘. 아직 구현하지 마.
2. **실행:** 확인한 계획대로 구현하고, 판단 기준·선택 이유·변경 내용을 기록해줘.
3. **검증:** 완료 기준에 따라 실제로 테스트하고 필요한 부분을 수정해줘.
   독립적인 기대값으로 결과를 확인하고, 검증 근거·미완료·미검증 범위를 정리해줘.

각 단계의 결과를 읽은 뒤 다음 단계를 요청합니다. 과제의 필수 파일명과 제출 양식이 있으면 우선합니다.

## 파일 구성

```text
skills/task-workflow/
  SKILL.md                 단계별 지침
  assets/DECISIONS.md       판단·검증·외부 자료 사용 기록의 빈 양식
  assets/REQUIREMENTS.md    요구사항과 검증 근거를 연결하는 빈 양식
  scripts/run_check.py      명령 실행·출력·종료 코드 기록 도구
tests/test_run_check.py     도구의 동작 검증
VALIDATION.md               이 도구 모음 자체의 검증 범위
```

양식은 과제에 도움이 되는 경우 필요한 부분만 작업 공간에 복사해 사용합니다.
양식의 빈칸이나 예시를 확인된 사실로 바꾸지 마세요.

자동 활성화하지 않았고, 이 키트와 결합한 실제 AI 작업 흐름도 검증하지 않았습니다.
`VALIDATION.md`의 테스트 결과는 이 키트 자체의 실행 도구에 관한 것입니다.

활용 여부는 작은 연습 과제에서 하나씩 비교해 판단합니다. 원인 파악·오류 발견·설명에 도움이 되는지와
소요 시간을 확인하세요. 전체 워크플로에는 작업 분리·리뷰 등의 절차도 있으므로 필요한 범위부터 검토합니다.
유명한 도구라는 이유만으로 해당 과제나 제한 시간에 적합하다고 가정하지 않습니다.

Codex 적용 방법은 [원본의 최신 안내](https://github.com/obra/superpowers#codex-cli)와 제공 환경의 규정을 확인하세요.
원본의 설치 안내가 있어도 실제 응시 환경에서 설치·설정 변경이 허용되거나 작동한다고 확인된 것은 아닙니다.
사용했다면 가져온 주소·커밋·라이선스·적용 범위와 검증 결과를 판단 기록에 남깁니다.

## 검증 명령 실행 도구

**검증할 과제의 디렉터리에서** 실행하세요. 아래 `KIT`은 Clone한 저장소의 실제 경로로 바꿉니다.

```sh
KIT=/path/to/hack-kit
python3 "$KIT/skills/task-workflow/scripts/run_check.py" --label regression --timeout 120 -- python3 -m unittest discover -s tests -v
```

이 명령의 `unittest ...` 부분은 과제의 실제 테스트 명령으로 바꿉니다. 테스트 도구를 자동 설치하거나
테스트 종류를 추측하지 않습니다. `--cwd`로 명령의 작업 디렉터리를 지정할 수도 있습니다.

한 번 실행할 때마다 호출한 위치의 `artifacts/checks/` 아래에 고유 폴더를 만들고 다음을 저장합니다.

- `stdout.log`, `stderr.log`: 실행 명령이 출력한 원본 바이트
- `result.json`: 실제 인수·작업 위치·시각·소요 시간·상태·종료 코드

로그는 터미널에 자동 재출력하지 않습니다. 종료 후 표시되는 폴더에서 읽으세요.
명령은 shell 없이 인수 그대로 실행하므로 `&&`, 파이프, 변수 확장은 자동 처리하지 않습니다.
대화형 입력은 지원하지 않습니다. 자격증명은 명령 인수에 넣지 마세요. 환경변수 전체를 로그로 수집하지 않습니다.

| 상황 | 도구 종료 코드 | result.json의 상태 |
| --- | --- | --- |
| 명령이 0으로 종료 | 0 | passed |
| 명령이 0 외의 값으로 종료 | 원래 종료 코드 | failed |
| 제한 시간 초과 | 124 | timed_out |
| 사용자가 중단 | 130 | interrupted |
| 실행 파일 없음 | 127 | spawn_error |
| 그 외 실행 시작 오류 | 126 | spawn_error |
| 인수·로그 저장 오류 | 2 | 실행 전이면 기록 없음, 저장 실패면 기록 불완전 가능 |

POSIX에서 신호로 종료된 명령은 `128 + 신호 번호`로 반환하며, 원래 음수 종료 코드도 기록합니다.
`passed`는 지정한 명령이 성공했다는 뜻입니다. 요구사항 충족 여부는 테스트의 내용과 기대값을 확인해 판단합니다.
성공·실패 출력 문구를 보고 종료 코드를 바꾸거나, 자동으로 재시도하지 않습니다.

도구 자체에는 네트워크 전송·AI 호출·git 조작 기능이 없습니다. 사용자가 지정한 명령의 동작은 별도로 확인해야 합니다.
시간 초과·중단 시 POSIX에서는 같은 프로세스 그룹을 종료하며, 다른 운영체제에서는 직접 실행한 프로세스만 종료합니다.
프로세스 그룹을 벗어나 분리 실행된 작업의 종료까지 보장하지 않습니다.

## 결과를 설명할 때

- 무엇이 문제였고, 어떤 입력·기록으로 확인했는가?
- 왜 그 방법을 선택했는가?
- 무엇을 비교해 맞다고 판단했는가?
- 실행하지 않았거나 아직 약한 부분은 무엇인가?
- AI가 수행한 일과 사람이 직접 판단·확인한 일은 각각 무엇인가?

검증에는 원자료·명세의 예시·독립적인 수작업 계산 등 해당 과제에 맞는 기대값을 사용합니다.
구현의 계산식을 그대로 테스트에 복사하는 것으로 검증을 끝내지 않습니다.
